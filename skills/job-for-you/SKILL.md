# job-for-you · 求职助手

三个子场景共享同一套输入（简历内容 + 目标岗位信息），彼此独立，用户要哪个就做哪个，不强求一次跑完整套。

## 何时使用

- 用户贴了简历内容/文件，并给出一个或多个职位描述（JD），要「匹配度」「差距」「要不要投」→ 场景 1。
- 用户要「模拟面试」「按 XX 岗位出题」「找 XX 岗位的面经」「整理题库」→ 场景 2。
- 用户要「找 XX 方向的职位」「推荐几个岗位」「这些职位里哪个更合适」→ 场景 3。

## 前置条件 / 权限

- 场景 2/3 用到 `o2` 的 `webcli` 浏览器驱动能力，首次使用需确认已完成：
  ```bash
  o2 install webcli
  webcli extension install   # 装 Browser Bridge 扩展，首次需手动在 chrome://extensions 加载
  webcli doctor               # 确认桥接连通
  ```
- 场景 3 抓取拉钩/BOSS 直聘等需要登录态的站点，依赖用户在 Chrome 里**已手动登录**该站点；本 skill 不做登录、不触碰账号密码，只做 `bind` 已登录标签页后的只读抓取。
- 场景 2 抓小红书面经走 `webcli xiaohongshu search`，默认限速（≥15s 间隔、≤30 次/天），首次调用需用户确认风险声明。
- 所有网络抓取均为**只读**，不在任何平台上发帖、投递、私信或执行写操作。

## 场景 1：简历-职位匹配分析

输入：简历文本（或用户粘贴的文件内容）+ 一个或多个目标 JD 文本。

步骤：
1. 从简历中提取：技能清单、项目经历（技术栈+量化成果）、工作年限、学历、期望方向。
2. 从每个 JD 中提取：硬性要求（学历/年限/技能关键词）、职责关键词、加分项。
3. 逐条比对，给出：
   - **匹配项**：简历中能直接对应 JD 要求的技能/经历。
   - **缺口项**：JD 要求但简历未体现或体现薄弱的点，区分「硬性缺口」（学历/年限类，难补）和「软性缺口」（技能/经验类，可短期补）。
   - **匹配度评分**（百分比或高/中/低），并说明评分依据，不要只给数字不给理由。
4. 给出可执行建议：简历里哪些经历该重新措辞/量化以贴合该 JD 关键词；软性缺口可以通过哪些项目/学习快速补齐。
5. 多个 JD 时，用表格横向对比匹配度和各自的核心缺口，帮用户排优先级。

输出：一份 Markdown 报告，含「匹配度总览表」「逐条比对」「简历优化建议」三段。不生成新简历文件，除非用户明确要求润色/改写简历本身。

## 场景 2：模拟面试与面经整理

两个子功能，按用户需求选用：

### 2a. 面经检索与整理
1. 先用 `webcli xiaohongshu search "<公司/岗位> 面经"` 搜索小红书笔记作为主要来源：
   ```bash
   webcli xiaohongshu search "<公司> <岗位> 面经" --limit 20 -f json
   ```
2. 其他平台（牛客、知乎、B站等）没有现成 webcli adapter，改用 `WebSearch`/`WebFetch` 检索公开页面补充。
3. 对抓到的内容：
   - 只保留**真实面经**（具体被问到的题目/流程/体验），排除招聘广告、求助帖、纯鸡汤/教程贴。
   - 按「技术题」「业务/场景题」「HR 题」分类去重整理成题库，每条标注来源平台（不编造来源）。
4. 输出一份 Markdown 题库，按分类列出题目，可选附上检索到的简要参考答案方向（标注「整理建议，非标准答案」）。

### 2b. 模拟面试
1. 以用户给定的岗位 JD（或 2a 整理出的题库）为依据出题。
2. 一次只问一道题，等用户回答后再给点评再问下一题，不要一次性甩一整屏题目——除非用户明确要「一次性列清单」。
3. 全部问完后做一次整体复盘：哪类问题答得好、哪类暴露知识盲区、针对盲区给练习建议。

## 场景 3：职位搜索与推荐

当前支持拉钩、BOSS 直聘，走 `webcli browser bind` 绑定用户已登录的标签页后只读抓取：

1. 提醒用户：在 Chrome 里打开目标平台（拉钩/BOSS 直聘）并登录，搜索出目标职位列表页，停在该页。
2. 绑定该标签页到一个浏览器会话：
   ```bash
   webcli browser jobsearch bind
   ```
3. 读取页面状态确认绑定到了正确页面：
   ```bash
   webcli browser jobsearch state
   ```
4. 用 `extract` 拿结构化/半结构化页面内容（职位名、公司、薪资、地点、要求摘要等）：
   ```bash
   webcli browser jobsearch extract
   ```
   列表页内容较长时用 `--start`/分页参数翻页抓取，不要漏页也不要重复抓同一页。
5. 需要翻页/点开详情时，用 `webcli browser jobsearch click/scroll` 等交互命令定位到下一页或详情，再 `extract`。全程只读：不点「投递」「申请」「立即沟通」等写操作按钮。
6. 抓完后：
   - 按用户给的筛选条件（城市、薪资、经验年限等）过滤。
   - 如果用户同时提供了简历，复用场景 1 的匹配逻辑，对每条职位给一个简要匹配度，按匹配度排序呈现。
   - 完成后 `webcli browser jobsearch unbind` 释放绑定，不要擅自关闭用户的标签页。
7. 输出一份 Markdown 职位列表：公司/职位/薪资/地点/匹配度(如有)/亮点或风险点，按匹配度或用户指定顺序排列。

## 影响面与回滚

- 场景 1/2b 纯文本分析，不产生外部副作用。
- 场景 2a/3 的网络抓取均为**只读**，不修改任何平台数据；`bind`/`unbind` 只是附加/解除会话绑定，不会关闭或登出用户的浏览器标签页。
- 不保存、不上传用户简历内容到本仓库之外的任何地方；分析结果只在当次对话中输出，除非用户明确要求落盘保存。

## 常见问题 / 排障

- `webcli doctor` 报桥接未连通：按提示跑 `webcli extension install`，在 `chrome://extensions` 手动加载扩展后重试。
- `bind` 后 `state` 显示的页面不是目标职位列表页：说明绑定错了标签页，先 `unbind` 再重新确认用户停在正确页面后重 `bind`。
- 小红书搜索命中内容多为广告/软文而非真实面经：扩大关键词覆盖（加公司全称/岗位别名），并用 WebSearch 补充其他平台，不要在候选不足时硬凑数量。
- JD 信息过短、关键词稀疏导致匹配分析不可靠时，如实告知用户「信息不足，匹配度仅供参考」，不要为了给出一个数字而编造依据。
